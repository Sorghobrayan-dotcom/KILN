The problem

Generating media is the easy part now — every provider does it. What breaks a small team is everything after.

  • Which prompt made this file? Which model? Can I make it again?
  • I regenerated that yesterday. I just paid for it twice.
  • Generated is not shippable. Where do I say “this one goes in”?
  • The build pins v2. Will v2 still be v2 in six months?

The proof

Kiln seals a version. A build pulls it, verifying every hash before a byte touches disk. This is that chain, run against the live bucket:

# seal what a human approved
providence v1 sealed with 6 assets
midnight-radio v1 sealed with 3 assets

# a build pulls it — one stdlib file, no Kiln install
$ python examples/pull.py …/providence/v1/manifest.json --into ./art-drop
providence v1: 6 pulled, 0 refused

# now alter one sha256 in the manifest
$ python examples/pull.py …/tampered.json --into ./art-drop
  REFUSED 000000…000000 — hash mismatch or missing url
providence v1: 5 pulled, 1 refused
$ echo $?
1   — the build stops

Two projects, one instance: a narrative game and a podcast. Nothing in the code knows what a game is.

How it uses Backblaze B2

B2 is not where Kiln puts files at the end. B2 is the database. The service holds no state, so it can be redeployed, replicated or killed without losing a decision anyone made — and the cache stays warm across deploys.

Assets

kiln/assets/ab/cd/<sha256> — content-addressable, so identical bytes occupy one key forever.

Manifests

kiln/manifests/<run>.json — Genblaze’s canonical provenance, hash-verified, one per run.

The step cache

<project>/cache/<key>.json — the piece the whole project rests on.

Sealed versions

<project>/v<N>/manifest.json — immutable. A build pinned to v2 keeps building the same thing.

How it uses Genblaze

Kiln does not wrap Genblaze. It extends it at three published seams.

A durable StepCache

The shipped cache is disk-backed: it dies with the container and is never shared between workers, so the same prompt is paid for again after every redeploy. Ours implements the same contract against B2.

A provider the SDK doesn’t ship

SyncProvider is public, so a Pollinations adapter is fifty lines rather than a fork. Its seed comes from the prompt hash — the same brief redraws the same picture.

A StorageBackend

An in-memory implementation, so the credential-free path runs the same sink and transfer code as production instead of skipping it.

Three things we found by using it

A cache hit is invisible

Genblaze returns the cached step verbatim — no flag, no tracer event — so an app can’t tell a hit from a fresh run, and can’t tell its user what was saved.

Cached before uploaded

A failed transfer leaves an entry pointing at a temp file the next process can’t read. That prompt then breaks permanently. We hit it three runs in a row.

Writes are path-guarded

Providers must write under temp or a declared output_dir. Correct, and invisible until a transfer fails citing allowed directories.

Built for a game studio because that is where I hit the problem. The loop — generate, judge, seal, never pay twice — belongs to any team producing media at volume.
