The problem

Making the picture is no longer the hard part

Any provider will do that for you. Small teams come unstuck afterwards, and none of it has to do with how good the model is.

  • Which prompt made this file? Which model? Can I make it again?
  • I regenerated that yesterday. I just paid for it twice.
  • Generated is not shippable. Where do I say “this one goes in”?
  • The build pins v2. Will v2 still be v2 in six months?

The proof

Sealing a version, then pulling it into a build

Kiln seals a version. A build then pulls it and checks every hash before writing anything to disk. Here is that chain against the live bucket.

# seal whatever a human approved
providence v1 sealed with 6 assets
midnight-radio v1 sealed with 3 assets

# a build pulls it. one stdlib file, no Kiln install
$ python examples/pull.py …/providence/v1/manifest.json --into ./art-drop
providence v1: 6 pulled, 0 refused

# now change one sha256 in the manifest
$ python examples/pull.py …/tampered.json --into ./art-drop
  REFUSED 000000…000000 (hash mismatch or missing url)
providence v1: 5 pulled, 1 refused
$ echo $?
1   # the build stops here

Two projects share one instance here, a narrative game and a podcast. Nothing in the code knows what a game is.

Backblaze B2

B2 is the database, not a cupboard

The service keeps nothing of its own. You can redeploy it, run four copies of it, or kill it outright, and no decision anyone made is lost. The cache is still warm afterwards.

SurfaceKeyWhy it matters
Assets kiln/assets/ab/cd/<sha256> Content-addressable, so the same bytes only ever take one key.
Manifests kiln/manifests/<run>.json One per run. Genblaze writes it and hashes it.
Step cache <project>/cache/<key>.json The part everything else here depends on.
Sealed versions <project>/v<N>/manifest.json Never rewritten, so a build pinned to v2 keeps building the same thing.

Genblaze

We extend Genblaze rather than wrap it

Three of its published extension points. We implemented them instead of working around them.

A durable StepCache

The cache that ships with Genblaze writes to disk. It dies with the container, and two workers never see each other’s entries, so you buy the same prompt again after every redeploy. Ours holds the same contract but writes to B2. It borrows Genblaze’s own step_cache_key, so the two always agree on what counts as the same step.

A provider the SDK doesn’t ship

SyncProvider is public, which made the Pollinations adapter fifty lines instead of a fork. We take its seed from the prompt hash. The same brief then redraws the same picture, so a cache hit matches a fresh run in the output and not only in the manifest.

A StorageBackend

An in-memory one. It means the path with no credentials still runs the same sink and transfer code as production, rather than quietly skipping it.

Field notes

Three things we ran into

A cache hit is invisible

Genblaze hands the cached step back as it was, with no flag and no tracer event. An app therefore cannot tell a hit from a fresh run, and cannot tell its user what it just saved them.

Cached before uploaded

A failed transfer leaves an entry pointing at a temp file the next process cannot read. From then on that prompt fails every time. It took three identical failures before we saw it.

Writes are path-guarded

Providers have to write under temp or a declared output_dir. That is the right call, and you will not hear about it until a transfer fails and mentions allowed directories.

A plumb line. Gravity, used to check whether a thing is true.

I built this for a game studio, because that is where the problem found me. The loop it runs suits any team turning out media in quantity: make something, judge it, seal it, stop paying twice.
